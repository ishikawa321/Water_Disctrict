# Android startup and issued-bill refresh

The 1.0.3 release was reproduced on a new, isolated Android 15 emulator. Its startup screen reported the same obfuscated `Bda` error as the phone screenshot. Android logcat identified `java.lang.NoSuchMethodError` for `SharedPreferencesApiRegistrar.getAll`, called while Supabase initializes persistent sign-in storage. This happens before login and does not require an older installation or a database change.

The app now requires `shared_preferences_android` 2.5.5 or newer, with compatible JNI dependencies locked in `pubspec.lock`. The upstream [Android preferences changelog](https://pub.dev/packages/shared_preferences_android/changelog) records the release-shrinking fix introduced in 2.5.2 and the corrected JNI generation in 2.5.5. Startup failures now offer Retry with a stable explanation; a partially initialized Supabase client is disposed before another initialization attempt. Session persistence and deep links remain enabled.

The main-branch Flutter client reads issued bills through `lib/billing_records.dart`. Consumer reads require an active account link and explicitly filter that account, in addition to Supabase RLS. Reads refresh saved interest and paginate both bills and verified payments. The dashboard, bill list and billing-history PDF use the same reader. The bill list starts on All bills, including paid bills and future due dates. A due date is a payment deadline, never a condition for displaying an issued bill.

Flutter bill/dashboard views refresh every 15 seconds while visible and on app resume, cancel their timers on disposal and prevent overlapping reads. The website's Consumer bills and summary also refresh every 15 seconds and on browser focus/visibility. Manual Refresh is available. This works without enabling Supabase Realtime or adding database permissions.

The fixed 28th-of-the-month rule has been replaced by Admin-selected release dates. The Admin Billing page opens its **Create a bill** form by default, with **Release bill date** and a separate due date. A release dated today is visible to the linked Consumer immediately after save/refresh, including before its due date. Future releases remain hidden by a restrictive Supabase SELECT policy until that Manila calendar date; this applies to the existing Android app as well as the website. The issued bill is already saved and visible to Admin/Staff with its scheduled release date.

Recurring plans have their own **Next monthly release date**. That selected day repeats monthly, using the last day for a shorter month and restoring the original day in subsequent months. Choosing today issues the initial bill on save. Recurring bills remain due three days after release, and daily simple interest is unchanged. Apply `database/billing-release-dates.sql` once after the previously installed billing/Staff setup; web publication alone cannot replace database functions or policies. Existing saved plan dates remain until Admin edits them.

Verification uses isolated HTTP/browser fixtures and an emulator created only for this task. Regression checks cover a bill added after the Consumer screen was already open, future due dates, active account scoping, payment totals beyond 500 receipts and retry after a startup failure. No production bill, payment, account link or profile is changed during these checks.

Released as Android 1.0.4 build 5 from main commit `11b76dd`. The actual signed APK reached sign-in after upgrading the failing version and after resetting the isolated emulator's app data; no missing-method exception appeared in corrected-release logcat. All 49 Flutter tests and 23 web browser workflows passed, along with 80 web unit checks, analysis/lint/type checks and the production build. The localhost Flutter sign-in and published website download were checked in Chrome. Production APK bytes and checksum matched the signed artifact.

## Merged 1.0.5 source

All remote branch tips (`main`, `UI-Redesign`, `feature/web-platform-parity`, and `feature/desktop-admin-staff`) are ancestors of the final merged source. The latest main branch's direct assigned-Staff repair resolution and Consumer home refresh are retained.

The Android Admin bill form now uses the atomic bill RPC with an explicit release date, a due date defaulting to release plus three calendar days, an automatically generated bill number, and a retained request UUID for safe retries. Manual bill-number and billing-period inputs are removed. Admin payment confirmation also uses the atomic RPC and generated 10-digit reference. Admin concern shortcuts and the Services tab use the authenticated native workspace for review, dispatch and repair assignment rather than the old desktop handoff. Staff actions retain database role/assignment restrictions.

The project operator reported successful execution of both `allow_staff_repair_resolution.sql` and `billing-release-dates.sql` during this update. Regression verification uses isolated data: 24 browser workflows, 89 web unit checks, 13 PostgreSQL role/workflow/release-date tests, 52 tests in the full Flutter suite plus the added focused Admin payment test, and clean Flutter analysis and web production build. No live financial or announcement records were written for testing.

The signed 1.0.5 build 6 APK from native source `c4a277a` was installed on the isolated Android 15 emulator both as an update and after uninstalling the prior app. Both runs reached the actual Flutter sign-in semantics, with no app-process missing-method or fatal exception in logcat. The initial emulator System UI not-responding dialog was dismissed before checking the update's screen. This is emulator verification, not a physical-device test. `apksigner` verified the existing release certificate, and `aapt` confirmed package `ph.maramag.waterdistrictconnect`, version 1.0.5/build 6, minimum SDK 24 and all three ABI libraries.
