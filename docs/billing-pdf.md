# Web billing PDF downloads

Admin and active Staff can open **Billing** and select **PDF** beside a bill to download its billing record, or **Download list PDF** to export the currently displayed list. Searching by bill or account number limits the exported list to those matching records. The list is limited to the 1,000 loaded records; it does not silently claim to export the entire database. An empty search result disables export.

Individual records include the bill number, service account, account holder and address, due date, original charge, accrued interest and day count, total charges, verified payment total and remaining balance. List reports include bill/account/holder details, due dates, the same financial totals and exact grand totals. Reports repeat headings across pages, use PHP amounts, identify the generating employee and show a generation timestamp in Asia/Manila. They describe saved balances at generation time, rather than serving as payment receipts.

The Node route `/api/office/billing-pdf` accepts a saved `billId` for an individual GET, or 1–1,000 `billIds` in a same-origin JSON POST for a list. It authenticates the active profile as Admin or Staff, uses that caller's Supabase session and existing row-level permissions, refreshes billing interest, then reloads bill/account records and all pages of verified payments. Browser-supplied amounts and names are ignored. Duplicate IDs are removed. If any selected record is unavailable or the data service fails, the entire request fails instead of downloading a partial or blank report.

PDF responses are attachments with private/no-store caching. The browser downloads the response directly and releases the temporary object URL. No PDFs are stored in Supabase or uploaded to an external document service. The renderer embeds the existing district logo and local DM Sans fonts; Vercel output tracing includes these assets.

This feature is web-only and needs no additional Supabase migration or private key. The existing active Staff role and billing setup remain prerequisites. Android and desktop download behavior is unchanged.

Verification uses isolated QA accounts and bills, not production customer writes. Unit checks cover role denial, malformed IDs, request limits, inaccessible records, service failures, exact payment aggregation beyond 500 receipts, duplicate selections and paginated 1,000-record PDFs. Browser checks download actual files as Admin and Staff, filter the list, recover from a failed export and deny Consumer/anonymous requests. Downloaded QA PDFs are also inspected for financial text, Unicode names and layout.
