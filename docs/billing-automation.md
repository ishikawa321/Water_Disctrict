# Billing and confirmed payments

Web and mobile continue to share the existing Supabase project and saved rows. No desktop or Render host is required.

## Apply to the existing project

An authorized owner runs these files in the project's [SQL Editor](https://supabase.com/dashboard/project/kaeespcylucvsazfdaks/sql/new), in order:

1. [database/billing-automation.sql](../database/billing-automation.sql): adds atomic billing/payment operations, number generation, recurring plans and interest. **As requested, this immediately applies overdue interest to existing unpaid bills from their original due date.** Already fully paid bills remain settled. Existing bill numbers, payment references, payments and account links are retained.
2. [database/billing-schedule.sql](../database/billing-schedule.sql): enables Supabase Cron and installs the named daily job. It runs at 16:05 UTC, which is 12:05 AM Manila time. The job persists independently of browsers, Vercel and the desktop. Rerunning replaces the same named schedule; it does not create duplicate jobs.

Refresh Billing. The automatic billing card reports whether the expected schedule is active. Set a monthly amount on each active service account and save it with automatic billing enabled. Accounts without an enabled plan are not issued recurring bills. Pausing stops future recurring issuance; existing unpaid bills still accrue interest.

Only the project owner can install SQL/Cron. The public key in Vercel cannot apply these migrations, so publication alone does not activate this feature. Missing setup retains drafts and reports the setup requirement; there is no legacy write fallback. No production financial records are used in automated tests.

## Issuance, numbers and dates

- Each enabled account receives one automatic bill per monthly issue cycle, on the 28th, with a due date three calendar days later. November 28 is due December 1. February 28 is due March 3 in a common year and March 2 in a leap year.
- The next eligible 28th is used when enabling a plan. Enabling on the 28th after the job has run issues that day's bill immediately. The job catches up missed pending cycles; a unique account/cycle index prevents duplicates. The plan amount used is the configured amount at issuance. Update it before the pending cycle if it must change.
- Generated bill numbers have the form `MWD-YYYYMM-1000000000`, globally unique and linked to the service account. The sequence suffix is not reused. Separate one-off bills can still be created; they do not replace the monthly cycle. The one-off form keeps account, amount and due date only; no bill-number or period input is required. Legacy period columns remain populated for existing clients/schema compatibility.
- Payment references are exactly 10 numeric digits, generated by a database sequence with collision checks against existing receipts. References are returned only after confirmation succeeds. Old references remain unchanged. Exhaustion fails safely rather than reusing references.

## Interest and confirmation

Daily interest is `round(original amount * 0.01 * overdue days, 2)`, starting the calendar day after the due date, using Manila dates. It is simple, not compound: a PHP 1,000 bill accrues PHP 10 per day, PHP 20 after two overdue days. Partial payments reduce the remaining balance but not the daily charge basis. Full confirmed payment freezes the charged interest and stops future accrual.

The original charge is preserved in `base_amount_due`; `interest_amount` and `interest_days` provide the breakdown. Existing `amount_due` stores original plus accrued interest, so the current Flutter APK's existing bill and dashboard queries see the same total on refresh. Web Consumer/Admin views show the breakdown, verified paid and remaining. There is no automatic realtime claim.

Payment confirmation locks the bill and catches up interest before validating the amount. Concurrent confirmations cannot overpay. The UI can fill the full currently displayed remaining amount; if it changes before confirmation, refresh before retrying. A request UUID makes a lost-response retry return the same payment/reference. Changing details under an already saved UUID is rejected. Bill creation has the same retry protection.

The payment date records the offline transaction date; full payment stops interest when district verification is recorded. Backdating the entered payment date does not erase already accrued charges. The Admin, actual verification time and generated reference are stamped by PostgreSQL. A narrow additive Admin policy uses Manila date and fixes the UTC-date rejection near local midnight. Existing role/account policies are retained; no public payment or Staff confirmation access is added.

## Scheduling and permissions

Private billing helpers and sequences are inaccessible to anonymous/authenticated callers. Public Admin RPCs validate the current active profile; `wd_billing_refresh` allows an active Consumer to catch up only their linked account's balances, or an Admin to catch up office balances. The scheduled routine cannot be executed through the authenticated Data API. A fixed search path and explicit actor checks constrain definer functions.

The nightly job issues due cycles and accrues interest. Read refreshes and payment confirmation catch up interest if the job was delayed; they do not create recurring bills. Monitor the job in Integrations > Cron and its run history. An active schedule indicator verifies configuration, not successful historical runs.
